## 二、事故根因：两个会话并发操作同一队列文件

另一 WorkBuddy 会话（工作目录为上级 `2026-09-27-00-43-30`）在 9/28 23:30–23:51 期间：

1. 备份 batch5 队列 → `发信队列-batch5备份.json`（快照 16 sent / 5 pending）
2. 新增 `构建跟进队列.py`，生成 38 封「跟进信」错峰队列
3. **23:51:57 覆盖 `发信队列.json`**，batch5 剩余 4 封被静默挤出（无报错）
4. 自行启动守候进程，运行至今正常（截至 01:11 已发 14 / 38）

关键点：`定时发送.py` 的队列路径 `QUEUE = ROOT / "发信队列.json"` 是**硬编码常量**，没有 `--queue` 参数，因此两个任务天然抢同一文件。

## 三、解决方案：独立队列（已实施）

新增 `补发batch5剩余4封.py`，与并发会话**完全隔离**：

- 只读写 `发信队列-batch5剩余.json`，**绝不触碰** `发信队列.json`
- 不启动守护进程、不碰 `.daemon.lock`（该锁属另一会话）
- 幂等：已 `sent` 的跳过，中断重跑不重发
- 只读信件原文与黑名单，只写自己的队列与日志

实测效果：补发推进期间，另一会话的跟进队列同步从 5 封走到 14 封，**两条流水线并行无冲突**。

用法：
```bash
python3 补发batch5剩余4封.py --status                    # 查看
python3 补发batch5剩余4封.py --run --send --yes          # 发已到点的信
```

## 四、环境限制（本次踩到的坑）

本机沙箱会**连带杀死 Bash 调用的整个后代进程树**：`nohup`、Python `start_new_session=True` 均无效（macOS 无 `setsid`）。单次 Bash 调用安全时长约 200 秒。

因此**跨小时的定时投递不能依赖单一长驻进程**。可靠做法是「调用方按窗口逐次驱动 `--run`」——本次 4 封补发即采用此法，每约 190 秒调用一次。
