# 02 · 执行步骤与输出契约

> **本文件职责**：定义本项目的执行流程与**输出字段（跨项目契约）**。
> 🔴 **输出字段是项目2 的输入契约，字段名与顺序不得擅改**（变更流程见 §三）。

---

## 一、输入 / 输出

| | 内容 |
|---|---|
| **输入** | ① 已开发客户名单（跟进表，73 行）② 产品信息（技能库） |
| **输出** | 候选公司清单（7 字段，见 §二） |
| **去向** | 项目2「客户信息挖掘」，由其负责找联系人与邮箱 |

---

## 二、输出字段（🔴 跨项目契约）

**字段名与顺序固定：**

```
公司名 | 国家/地区 | 行业 | 公司规模 | 产品线 | 来源链接 | 推导理由
```

### 字段定义

| # | 字段 | 定义 | 取值要求 | 本项目如何获得 |
|---|---|---|---|---|
| 1 | **公司名** | 公司全称 | 优先法定全称；若只有商用名，写商用名并标注 | 检索获取 |
| 2 | **国家/地区** | 国家 + 州/省 | 格式：`国家 · 州/省 城市`（与跟进表一致） | 检索获取 |
| 3 | **行业** | 行业分类 | 🔴 **不等于 `买家类型`**，但可含类型标注（如"电气承包商 / 公用事业"） | 检索获取 |
| 4 | **公司规模** | 员工数或规模档 | 第三方估算须标注来源；**未获取则写"未获取"** | 🔴 **需外部检索**（数据源A 无此列） |
| 5 | **产品线** | 对方可能采购的 JZP 产品 | 对应 `02-products.md` 的产品形态名 | 由画像+产品矩阵推导 |
| 6 | **来源链接** | 可验证来源的完整 URL | 🔴 **必须可点击、可回源**（红线 1） | 检索获取 |
| 7 | **推导理由** | 凭什么判定他是目标客户 | 1–3 句，须含：客户类型 + 匹配的产品 + 关键证据 | 本项目推导 |

### 输出示例（格式示意）

```
B.G. High Voltage Systems Limited | 加拿大 · 安大略省 Scarborough | 电气承包商 / 高压专业服务商 | 未获取（AllBiz 记 25–100，RocketReach 记 2，差异大） | 干式变压器、液体变压器、开关柜 | https://www.bg-high-voltage.ca/ | 【B 型 EPC/承包商】1987 年成立的联邦注册电气承包商，主营变压器与变电站的规划安装维护（最高 245 kV），官网明确列出干式与液体变压器安装维护为主营板块，属变压器的直接使用方与采购方，非中间贸易商。⚠️ 但该主体已在本项目排重命中（跟进表 #1），仅作格式示意
```

> ⚠️ **提交前必须对每一家执行排重**，上面示例中的公司实际**应被剔除**。

### 与项目2 字段的衔接说明

| 情况 | 处理 |
|---|---|
| 项目2 需要联系人与邮箱 | ❌ **本项目不提供**，这是刻意的（见 `01` §五）。项目2 自行挖掘 |
| 项目2 需要 `公司规模` 压数字 | 本项目提供时须标注来源；未获取则写"未获取"，由项目2 补充 |
| 字段增删/改名/换序 | 🔴 **必须走 §三 变更流程**，同步更新项目2 的 `03_input_contract_from_project1.md` |

## 三、契约变更流程（🔴 不可跳过）

若确需修改 §二 的字段：

1. **列出改动点**（原文 → 新文）等**用户确认**
2. 获批后，**同步更新**以下两处，必须**逐字一致**：
   - `project2/03_input_contract_from_project1.md` §一
   - `project2/01_execution_steps.md` §一「输入字段」
3. 检查是否需要**同步告知项目3**（若字段传递到项目3）
4. 在本文件与 `00` 文件记录变更

**"格式变化"包含**：字段增删、字段改名、字段顺序调整、分隔符变更。

> 🔴 **改一侧不改另一侧 = 项目2 读取失败或字段错位。**

## 四、执行步骤

```
① 前置检查
   └─ 运行 00_readiness_check.py
   └─ 任何 [STOP] → 停止并报告；有 [WARN] → 显著向用户提示后继续

② 建立画像锚点（从数据源A 提炼）
   └─ 读跟进表 73 行的 买家类型 / 需求产品 / 国家地区 分布
   └─ 读技能 09-customer-profile.md 的五类客户 + 产品×客户矩阵 + 地域画像
   └─ 读 03_profile_pattern_notes.md 作辅助参考（⚠️ 03 不是数据源，以表格实际数据为准）
   └─ 读技能 02-products.md 确定当前重点产品及其目标客户特征

③ 推导候选公司
   └─ 按 01 §一 五层标准检索/推导
   └─ 地域优先：加拿大安省 → 美国 CA/AK/AL/WV → 其他

④ 逐家执行目标客户判定
   └─ §1.1 价值链位置（必要条件，不满足直接淘汰）
   └─ §1.2 客户类型归属（五选一，写依据）
   └─ §1.3 产品形态匹配（至少一个）
   └─ §1.4 地域加权、§1.5 规模参考
   └─ 结论落到：✅目标客户 / ⚠️疑似 / ❌不符合

⑤ 排重（🔴 红线，逐条比对，不可抽样）
   └─ 加载 00_readiness_check.py --write-master 产出的主表
   └─ 公司名标准化比对（主键）+ 邮箱域名比对（辅助）
   └─ 命中 → 剔除；疑似同名 → 标注交人工判
   └─ 🔴 统计并报告："本次推导 N 家，排重剔除 M 家"

⑥ 来源核验（🔴 红线 1）
   └─ 每个候选必须有可打开的来源 URL
   └─ ❌ 无来源的 → 直接剔除，不输出
   └─ 二手来源 → 标注来源类型

⑦ 输出
   └─ 按 01 §四 优先级排序
   └─ 7 字段固定格式
   └─ 附数据源健康状态 + 排重剔除统计 + 缺口清单

⑧ 相关性复筛（🔴 结果发出前必做，见 `05_relevance_review.md`）
   └─ 对排重后剩余的 R 家逐家打分（5 维 0–2 分，满分 10；一票否决项直接剔除）
   └─ 未过线（< 6 分）→ 剔除或回炉补证据，**不凑数输出**
   └─ 输出复筛报告（保留/剔除/回炉数量 + 每家得分 + 剔除原因）
```

## 五、输出交付物格式

每次运行的交付物应包含以下 5 部分（**缺一不可**）：

### 1. 数据源健康状态
（`00_readiness_check.py` 的输出，任何 ⚠️ 须显著标出）

### 2. 候选清单（主体）
7 字段，按优先级排序。

### 3. 排重剔除报告
```
本次推导：N 家
排重剔除：M 家（命中跟进表）
  ├─ 公司名命中：M1 家
  └─ 域名命中：M2 家
疑似同名待确认：K 家
最终输出：N - M = R 家
```

### 4. 缺口清单
本批次中被标 `⚠️ 疑似` 的公司及其待确认项，以及检索失败的信息。

### 5. 相关性复筛报告（🔴 ⑧ 的产出，不可省略）
```
复筛对象：R 家（排重后剩余）
保留：P 家（≥ 6 分）/ 剔除：Q 家 / 回炉补证据：S 家
每家一行：公司名 | 总分/10 | 五维分项 | 结论（保留/剔除/回炉）| 剔除原因
```
> 🔴 **第 3、5 部分不可省略** —— 分别是用户核对"排重是否真的生效"和"复筛是否真的执行"的唯一依据。

---

## 六、批量与批次管理

- 单批 **30–50 家**（默认建议 40，生效值见 `01` §六 第 6 项）
- 每批输出独立文件，命名：`outputs/候选清单_YYYYMMDD_batchN.md`
- 批次间**仍须逐家排重**（不能因"上一批已排过"就跳过）
- ⚠️ 若本批与上批有重叠候选，需说明去重结果

---

## 七、自检清单（每次交付前逐项核对）

- [ ] 前置检查已运行，无未解决的 [STOP] 项
- [ ] 数据源健康状态已在交付物开头展示
- [ ] 每家公司都做了 §1.1 价值链位置判定（没有漏掉终端用户/纯贸易/同行的淘汰）
- [ ] 每家公司都归入了客户类型 A–E，并写了判定依据
- [ ] 每家公司都指出了至少一个对应产品形态
- [ ] **每家公司都有可打开的来源链接**（红线 1）
- [ ] **排重逐条比对已执行**，且报出了剔除数量（红线 2）
- [ ] 产品匹配真实，没有为凑数推荐无关产品线（红线 3）
- [ ] 未获取的信息写"未获取"，没有编造（红线 4）
- [ ] 未修改任何数据源文件（红线 5）
- [ ] 输出字段与项目2 契约**逐字一致**
- [ ] **相关性复筛已执行**（`05` 清单逐家打分，一票否决已剔除，未过线一律不输出）
- [ ] **复筛报告已附**（保留/剔除/回炉数 + 每家得分 + 剔除原因）
