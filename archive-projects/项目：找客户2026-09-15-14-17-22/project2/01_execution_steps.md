## 二、执行步骤

1. **定位该公司的关键决策人角色**（采购 / 销售负责人等，**优先级由用户定义**）
2. 🔴 **先锁定具名决策人（L-1）**，并做 **still_here 在职核验** —— 见下方「步骤 2 的展开 2.1/2.2」
3. **查找该决策人邮箱**，进行**格式校验和交叉确认**（见 `00_core_rules.md` H3/H4/H6）
4. **查找该决策人的职业社媒**（领英等）
5. **进行背调**，总结成简要摘要（**以公开职业信息为主**）
6. **按 `00` 中的合规边界检查**，标注任何需要用户注意的风险点

### 步骤 0（隐含前置）：收到输入后的第一动作
- 🔴 **先查重**：在 `buyers/` 下检索该公司是否已做过 → 做过就立即告知用户，**不重复劳动**
- 再核对项目1 给的 7 个字段（尤其"来源链接"要回源）

### 步骤 2 的展开（邮箱：最易出错的一步）

> 🔴 **核心原则（2026-09-23 升级）：先锁「人」，再找「邮箱」。**
> 链条 = `域名 → 公司 → 正确的人 → 已验证邮箱`，**每一步都应收窄**。
> **只拿到 `info@` 不算完成** —— 这个邮箱价值低，是因为它背后没有人。

#### 2.1 【新增前置层】L-1 锁定「具名决策人」（最优先，必做）

| 步 | 动作 |
|---|---|
| ① | 先判买家类型 + 公司规模 → 查角色映射表，锁定目标职能词（**头衔随规模漂移，不能一律搜 CEO**） |
| ② | 抓 LinkedIn 公司页 → Employees 名单逐个 dork；有 People 区则按职能/层级视角筛 |
| ③ | 跑 4 组强制 query（公司页 slug / 公司快照 / 员工清单 / 头衔核验） |
| ④ | 小微兜底：**组织图反推**（找任一员工 → 看谁 tag 谁 / endorsement / "People also viewed" → 反推老板） |

- **通关标准**：拿到 ≥1 份「**姓名 + 职能 + 在职证据 + 个人页 URL**」
- 🔴 **拿到人之后必须立刻做 still_here 在职核验**（见 2.2）
- 🔴 **未锁定具名决策人**：允许继续走邮箱链，但**必须在交接单写明「L-1 未锁定具名决策人」**，并自动触发 2.4 的升级三步

#### 2.2 【强制】still_here 在职核验（任何邮箱进主送前必做）

> **依据**：B2B 联系人**每年约 18–20% 换工作**；数据衰减约 2.1%/月；37.3% 的邮箱 12 个月内失效。
> **不核就发 = 发给已离职的人。**

| 检查项 | 判定 |
|---|---|
| 个人页 current 公司 = 目标公司？ | ≠ → **离职风险 🔴，该邮箱作废** |
| 任职时长 < 30 天 | **新入职** → 改走「恭喜/欢迎」角度，**邮箱格式可能不同** |
| 个人页最近活跃 | 有近期活跃 = **still_here 正面证据 ✅** |
| 多人/多源同期提及 | 加强在职可信度 |

**核验结果写入交接单四栏**：`在职称谓 / 任职时长 / 最近活跃 / 离职风险`。

#### 2.3 主体邮箱链（L0→L7 顺序不变）

- **L0** 官网全量（含角色邮箱、页脚、PDF、`og:description`、Cloudflare `data-cfemail` 解码）
- **L1** 政府一手源（FMCSA / SAM.gov / 州执照库 / 投标文件）—— **政府邮箱 > 官网通用邮箱**
- **L2** 命名规则 + DNS（MX/TXT，有样本才可推演）—— **免费第一跳：直接推演，约 1/3 命中**
- **L3** B2B 库交叉（**两库互证不算印证**）
- **L4** 社媒与协会（**LinkedIn 第二岗**：头衔核验 + still_here + 公司页 JSON-LD）
- **L5** 本地黄页与同址（用公司地址反查）
- **L6** 电话/表单兜底（点名转交）
- **L7** 付费 API 预留（无 API 时标注"未启用"）

#### 2.4 【硬规则 H6】角色邮箱升级三步（唯一收获是 `info@` 时强制）

| 步 | 动作 |
|---|---|
| ① | 挖职能邮箱：读 Contact / Team / Careers 页，找 `Supplier@` / `Owners@` / `Estimating@` / `Purchasing@` |
| ② | 从该域名任何真实回信的**显示名 / 签名**反推命名规则 |
| ③ | 免费先试推演（约 1/3 命中，成本≈0） |

🔴 **三步全失败 → 交接单必须写「仅取得角色邮箱 `info@`，未取得决策人直邮」，并列为本条风险。禁止混在「邮箱」字段里蒙混过关。**

#### 2.5 邮箱 A/B/C 三档（交付分档）

| 档 | 类型 | 可否主送 |
|---|---|---|
| **A** | 具名决策人邮箱（Valid） | ✅ 主送 |
| **B** | 角色邮箱（`info@`/`sales@`） | ⚠️ **仅点名转交** |
| **C** | 免费邮箱 / Catch-all | 🔴 需电话确认 |

#### 2.6 推演邮箱「可执行阶梯」

逐个实测（**不批量盲发**），配合对照测试（先测已知真实的 `info@` 排除工具假阴性）：
```
{first}@ → {first}.{last}@ → {last}@ → {fi}{last}@ → {fi}{li}@
```

**置信度**：政府/官网明文 +2；第二独立源 +2；样本印证 +1；B2B 单源 +1；纯推演 0；catch-all −2。
**≥4 分才可作主送**；**≤2 分只能备选 + 电话验证**。

**停止规则**：① 拿到具名决策人直邮（≥4 分）可停 L3–L5（L1 已查）；② 仅有角色邮箱时 **L-1 至 L6 全走完 + 必跑升级三步**；③ 交接单必须附**覆盖清单表**（**L-1、L0–L7** 每行 ✅/⚠️/❌）。


| 1 | **公司名** | 与输入一致；含法律实体名与 dba |
| 2 | **联系人姓名** | 关键决策人；无则写"未找到"并给出转交策略 |

| 4 | **邮箱** | 主送用**已验证**地址（**A 档**）；推演地址列为备选并标注；**角色邮箱（`info@`）属 B 档，仅作点名转交，不得作主送**（见 `00` H6） |
| 5 | **邮箱验证状态** | `已验证` / `待验证` / `未找到`（判定标准见 `00` H4）；**另按 A/B/C 三档标注邮箱类型**（A 具名 / B 角色 / C 免费或 catch-all） |
| 6 | **社媒链接** | 领英优先；个人页与公司页分列 |

| 8 | **信息来源** | 每个关键字段的来源清单（含印证数） |
| 9 | **合规风险提示（如有）** | 地址陷阱 / 域名归属异常 / 经营状态存疑等 |

### 3.2 扩展段（第 10 项「补充信息」，交给项目3 写信用）

> 项目3 依赖这些内容写开发信，**不可省略**。各段内部结构如下（沿用历史交接单的成熟分节）：

| 段 | 里面有什么 | 项目3 怎么用 |
|---|---|---|
| **标准字段明细** | 国家+城市 / 详细地址 / 电话 / LinkedIn / 网站 / 成立日期 / 员工规模 / 年营收 / NAICS / PSC | 决定收件人与产品切片 |

| **邮箱分档（A/B/C）** | A 具名决策人 / B 角色邮箱 / C 免费或 catch-all | 决定主送还是仅点名转交 |

| **采购信号** | 分销商身份 / 仓库 / 投标职能 / 扩张战略等 | 决定钩子强度 |
| **可利用的「钩子」（按强度排序）** | 已排序；⚠️ 落点必须在己方真有产品上（**己方产品清单见 §3.2.1**） | 项目3 会重新筛，不直接抄 |
| **开发信建议** | 开场角度 / 收件人策略 / 送达建议 | 强烈参考 |
| **⚠️ 矛盾点与风险提示** | 网关 / 同名公司 / 域名异常等 | 红线清单 |
| **信息缺口清单（请勿编造）** | 明确列出不能写的字段 | 🔴 逐条对照写作 |
| **一句话画像** | 便于快速理解客户 | 通读替代 |
| **渠道覆盖清单（L-1、L0–L7）** | 每行 ✅/⚠️/❌ + 一句话 | 显示挖掘是否穷尽 |

### 3.2.1 🔴 写「需求品类 / 钩子」前必查己方产品能力边界

> **2026-09-23 新增。** 此前本项目的「需求品类」只写产品名词（如"干式变压器"），
> 结果项目3 收到后才发现**该品类我方无 UL、对美国客户根本不匹配** → 白挖。
> **根因：不是挖得不好，是没人把"我方能力边界"交给本项目。**

**己方产品能力边界（可直供 / 条件切入 / 不匹配）的唯一事实来源：**

```
~/.workbuddy-ai/skills/jzp-company-knowledge/references/10-capability-boundary.md
```

**写「需求品类」时按此规则落笔：**

| 客户要的品类 | 我方结论 | 「需求品类」字段应写成 |
|---|---|---|
| 三相美变 / 主变（参数在 UL 区间内） | ✅ 可直供 | `三相美变（UL E541627，可直供）` |
| 单相柱上变 / 单相美变 / 小主变 | 🟡 仅条件切入 | `单相柱上变（认证在办，条件切入）` |
| 干式变压器 + 美国客户 | ❌ 不匹配 | `干变（美国不匹配：无 UL）` ← **必须写"不匹配"，不能只写"干变"** |
| 500 kV 级输电设备 | 🟡 产能可覆盖、UL 区间外 | `主变/变电站变（产能可覆盖，UL 区间外，需人工确认）` |
| 只知行业、不知品类 | — | `（未定位，需电话确认）` |

**三条硬规则：**

1. **品类字段必须带结论态** —— 不要只丢一个产品名词。这是本项目改动成本最低、
   对项目3 增益最大的一项。
2. **❌ 不匹配的品类要显式标注**，不要因为"客户确实要这个"就照实写。
   显式标注能让项目3 **主动回避**该话题，避免自曝短板。
3. **钩子落点必须落在「✅ 可直供」或「🟡 条件切入」上** ——
   ⛔ **绝不把钩子挂在 ❌ 不匹配的品类上**（例：对美国干变客户写"我们干变做得很好"）。

> ⚠️ 该技能文件是**摘要**，冲突时以开发信项目 `project3/02_product_positioning.md` 为准。
> 判断有疑问时 → 在交接单里写"需人工确认"，**不要自行推测我方能力**。
